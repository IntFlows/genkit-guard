# Benchmarks and deployment sizing

The rc.1 run is accepted with a documented memory limitation. The user selected
concurrency **10** and generation p95 **<=9 seconds** on 2 November 2026.

| Measure | Result |
| --- | --- |
| Target phase | 799 conversations over 1,809.4 reported seconds |
| Unexpected errors | 0 |
| Generation p50 / p95 / p99 | 5,358 / **7,889** / 12,837 ms |
| Conversations/s | 0.442 |
| JSON restorations / expected injection rejections | 79 / 79 |
| Redis expiry / clock continuity | Pass |
| Baseline / final median RSS | **2,249 / 3,107 MiB** |
| Relative-memory criterion | Failed; accepted as an RC limitation |

Measurements use cached MiniLM/privacy-filter q4 inference, real Redis and a
controlled Genkit provider on an Intel Core 7 240H, WSL2, Node.js 22.22.1,
Genkit 1.42.0 and Redis 8.10.2. They exclude live Gemini latency and do not establish
PII recall or a universal SLA. Latency covers successful generations including
the initial tool loop; throughput counts complete conversations.

The raw failed memory result is preserved. The exception covers this reviewed
run only; stable v1 still requires the representative 24-hour production soak
and long-term memory validation. The cause of the RSS increase is not established.
Concurrency-50 stress failures remain documented and are outside this RC target.

Full methods, historical results, archive identities and raw reports are in the
repository's `docs/benchmarks.md`, `docs/rc.1-readiness.md` and
`docs/validation/rc-2026-11-02/`. The measured harness used per-conversation Genkit
registration; later reusable-worker diagnostic runs are not substituted for it.

The default memory vault has no TTL/capacity bound. Redis TTL is per hash and
refreshes on writes; continuous traffic can retain the token index indefinitely.
Monitor cardinality and memory, not just key count. Use a custom adapter for hard
per-entry retention limits, isolate trust boundaries, and provide application
idempotency before retrying ambiguous tool execution.
